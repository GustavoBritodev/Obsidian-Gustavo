O Protocolo de Servidor de Linguagem (LSP) é um protocolo aberto baseado em JSON-RPC para uso entre editores de código-fonte ou ambientes de desenvolvimento integrado (IDEs) e servidores que fornecem "ferramentas de inteligência de linguagem": recursos específicos de linguagens de programação como autocompletar código, realce de sintaxe, marcação de avisos e erros, e rotinas de refatoração. O objetivo do protocolo é permitir que o suporte à linguagem de programação seja implementado e distribuído independentemente de qualquer editor ou IDE específico. No início da década de 2020, o LSP rapidamente se tornou uma "norma" para fornecedores de ferramentas de inteligência de linguagem.

## Histórico

O LSP foi originalmente desenvolvido para o Microsoft Visual Studio Code e agora é um padrão aberto. Em 27 de junho de 2016, a Microsoft anunciou uma colaboração com a Red Hat e a Codenvy para padronizar a especificação do protocolo. O protocolo foi originalmente apoiado e adotado por essas três empresas. Sua especificação é hospedada e desenvolvida no GitHub.

## Contexto

Os IDEs modernos fornecem aos programadores recursos sofisticados como autocompletar código, refatoração, navegação para a definição de um símbolo, realce de sintaxe e marcadores de erro e aviso.

Por exemplo, em uma linguagem de programação baseada em texto, um programador pode querer renomear um método chamado "ler". O programador poderia editar manualmente os respectivos arquivos de código-fonte e alterar as ocorrências apropriadas do nome antigo do método para o novo nome, ou usar os recursos de refatoração de um IDE para fazer todas as alterações necessárias automaticamente. Para poder suportar esse estilo de refatoração, um IDE precisa de uma compreensão sofisticada da linguagem de programação em que a fonte do programa está escrita. Uma ferramenta de programação sem essa compreensão - por exemplo, uma que realiza uma pesquisa e substituição ingênua - pode introduzir erros. Ao renomear um método "ler", por exemplo, a ferramenta não deve substituir a correspondência parcial em uma variável que pode ser chamada de "readyState", nem deve substituir a parte de um comentário de código contendo a palavra "já". Também não deve renomear uma variável local "ler", por exemplo, alterando variáveis com nomes idênticos em outros escopos.

Compiladores ou interpretadores convencionais para uma linguagem de programação específica normalmente não podem fornecer esses serviços de linguagem, porque são escritos com o objetivo de transformar o código-fonte em código objeto ou executar o código imediatamente. Além disso, os serviços de linguagem devem ser capazes de lidar com código-fonte que não está bem formado, por exemplo, porque o programador está editando e ainda não terminou de digitar uma declaração, procedimento ou outro construto. Além disso, pequenas alterações em um arquivo de código-fonte feitas durante a digitação geralmente mudam a semântica do programa. Para fornecer feedback instantâneo ao usuário, a ferramenta de edição deve ser capaz de avaliar rapidamente as consequências sintáticas e semânticas de uma modificação específica. Portanto, compiladores e interpretadores fornecem um candidato inadequado para produzir as informações necessárias para uma ferramenta de edição consumir.

Antes do projeto e implementação do Protocolo de Servidor de Linguagem para o desenvolvimento do Visual Studio Code, a maioria dos serviços de linguagem geralmente estava vinculada a um determinado IDE ou outro editor. Na ausência do Protocolo de Servidor de Linguagem, os serviços de linguagem são normalmente implementados usando uma API de extensão específica da ferramenta. Fornecer o mesmo serviço de linguagem para outra ferramenta de edição requer esforço para adaptar o código existente para que o serviço possa direcionar as interfaces de extensão do segundo editor.

O Protocolo de Servidor de Linguagem permite desacoplar os serviços de linguagem do editor para que os serviços possam ser contidos em um servidor de linguagem de uso geral. Qualquer editor pode herdar suporte sofisticado para muitas linguagens diferentes, utilizando servidores de linguagem existentes. Da mesma forma, um programador envolvido no desenvolvimento de uma nova linguagem de programação pode disponibilizar serviços para essa linguagem para ferramentas de edição existentes. Fazer uso de servidores de linguagem por meio do Protocolo de Servidor de Linguagem também reduz a carga sobre os fornecedores de ferramentas de edição, porque eles não precisam desenvolver serviços de linguagem próprios para as linguagens que pretendem suportar, desde que os servidores de linguagem já tenham sido implementados. O Protocolo de Servidor de Linguagem também permite a distribuição e desenvolvimento de servidores contribuídos por terceiros interessados, como usuários finais, sem envolvimento adicional do fornecedor do compilador para a linguagem de programação em uso ou do fornecedor do editor ao qual o suporte de linguagem está sendo adicionado.
